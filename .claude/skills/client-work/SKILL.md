# 受注案件対応ガイド

このリポジトリのジェネレーター（formats/templates/elements の辞書群）を**業務の納品パイプライン**として使う。案件処理の中核は `/order` コマンド。

## 業務フロー（5ステージ）

```
受注 → ①ヒアリング → ②構成案の確認 → ③デザイン制作 → ④納品 → ⑤評価依頼
```

| ステージ | 使うもの | 定型文 |
|---|---|---|
| ①受注直後 | `business/hearing-form.md` を送付 | `message-templates.md` §1 |
| ②構成案 | `/order <ヒアリング回答>` で生成 → クライアント確認 | §2 |
| ③制作 | 構成案を元に Canva で制作（人間の作業） | — |
| ④納品 | `business/delivery-template.md` 形式 | §3 |
| ⑤その後 | 評価依頼 → 2回目の顧客には月間プラン案内 | §5, §6 |

## 鉄則

1. **構成案の確認を必ず挟む**（②を飛ばすと手戻りでデザイン工数が全損する）
2. **修正は復唱してから着手**（§4。範囲外の修正は追加オプションを案内）
3. **納品には+1情報を添える**（投稿時間帯の提案など。評価が上がる）
4. **秘密保持**: クライアント名・納品物は `business/deliverables/`（git管理外推奨）にのみ保存。SNSや実績公開は書面の許可を得てから
5. **値引きに応じない**。代わりに枚数・範囲の調整を提案

## 品質基準

- 構成案は `writing-rules.yaml`（14項目）+ `quality-checklist.yaml`（16項目）を必ず通す
- 抵触の可能性は「リスクフラグ」として納品文書に明記（勝手に判断せず通知）
- 業種が薬機法・金融など規制領域の場合、その旨をクライアントに確認する一文を構成案確認時に入れる

## 関連ファイル

- `business/hearing-form.md` … クライアント送付用フォーム
- `business/message-templates.md` … 全ステージの定型文
- `business/delivery-template.md` … 納品文書の雛形
- `business/sales/` … 出品文・価格・営業資料（実勢価格の根拠つき）
