# ハーネスエンジニアリング（自律開発の型）

出典: `raw/2026-07-ハーネスエンジニアリング開発実況.md`（YouTube開発実況）。
一言で: **「AIに実装させる前に、合否を自動判定する“治具（ハーネス）”を先に組む」**開発の型。

## 何が違うのか（ループエンジニアリングとの対比）

| | ループエンジニアリング | ハーネスエンジニアリング |
|---|---|---|
| やり方 | 「テスト通るまで回して」と丸投げ | 実装役とレビュー役を**分離**、レビュー役が**実ブラウザでE2Eテスト**して合格時だけ次へ |
| 合否判定 | AIの自己申告（甘くなる） | 外部の客観テスト（Playwright）が門番 |
| 人間の役割 | 祈って待つ | **治具の設計**と**何を作るかの意思決定** |

核心: 「テスト合格まで回す」だけでは足りない。**合格の基準を人間が治具として外部化**するのが本質。

## 3段ワークフロー（そのまま真似できる）

1. **壁打ち**: AIと要件を固める（何を・どこまで作るか）
2. **ハーネス設計**: サブエージェントを2種つくる
   - 実装用サブエージェント（チケットを1つずつ実装）
   - レビュー用サブエージェント（**Playwright MCPでブラウザを立ち上げE2Eテスト → 合格した時だけ次のチケットへ**）
3. **自律実装**: 要件を全部投げてバックグラウンド実行。約5〜6時間・15チケットを人間ノータッチで完成

## あなたの既存資産との接続（ここが重要）

**あなたは既にハーネスの部品を持っている。組み合わせるだけ。**
- `.claude/agents/` の**サブエージェント6役** … 実装役／レビュー役の分離は極限起動の「生成者×破壊者」と同じ構造
- `gokugen-destroyer`（破壊者）= まさに**レビュー用ハーネス**。褒めずに壊す門番
- `gokugen-finisher`（仕上げ屋）= 合格後に出荷状態へ整える役
- 足りない1ピース = **Playwright MCPで実ブラウザ判定**する自動E2E。これを破壊者に持たせると「動くかどうか」まで客観判定できる

→ 次の実装課題: 破壊者エージェントに Playwright MCP を接続し、「画面が実際に動くか」を合否ゲートにする。

## モデル・スタックの割り切り（ROI視点）

- **最新モデルに拘らない**: 「Fable 5 が使えなくても Opus 4.8 でハーネス設計すれば同じ」。モデル待ちは言い訳になる
- 個人開発Webは **Cloudflareスタック**に寄せる（D1/Workers/R2 + Wrangler CLI）と Claude Code 上で完結して楽
- 認証は **Better Auth** が無難（Clerkは無料枠の制約がきつい）

## 出荷ファーストとの接続（最重要）

発言者の結論: **「1番大事なのは“売る”という最後のワンピース」**。
ハーネスをいじり回すのは楽しいが、それは準備。作って → リリース → マネタイズに向き合うのがボトルネック。
→ `concepts/出荷ファースト.md` と完全に一致。**ハーネスは“速く出荷するための道具”であって、目的ではない。**

## 人間にしか出せない判断（AIに委譲できない部分）

- 「何を追加するか／技術的負債をどこまで許容するか」= 言語化できない蓄積・その日の気分にも左右される
- プロンプト自体をAIに考えさせる = 意思決定の丸投げ。**実装は任せ、判断は握る。**

### 大元はOpenAIの記事
- 用語の火付け役は **OpenAIの2026年4月ブログ "Harness Engineering"**（Codexをエージェント前提で使う話）。Martin Fowlerも記事化＝一過性のバズでなく定着した概念
- AI活用の進化は3段階: **プロンプトエンジニアリング → コンテキストエンジニアリング → ハーネスエンジニアリング**。2026年は第3段階
- 定義: **AIモデル“以外”すべての設計**。エージェントを取り囲む「使えるツール／ガードレール／自己修正のフィードバックループ／観測レイヤー」を作る技術

### 本番グレードのハーネス＝5層
1. **ツールオーケストレーション** … エージェントが呼べるツールと、その多対多の関係を設計
2. **検証ループ（verification）** … テスト・E2E等で自動合否判定（＝実況動画の「レビュー役ハーネス」はここ）
3. **コンテキスト／記憶** … 有限のコンテキストを管理。残量が減ると**「コンテキスト不安」**に陥り、手抜き実装や早すぎる「完了」宣言が起きる → 分割・要約で防ぐ
4. **ガードレール** … 入力バリデーション＋出力フィルタ＋ツールのリスク格付け＋人間介入トリガーの多層
5. **観測（observability）** … 人間が挙動を監視できる層

### 運用は3層に分ける（2026の標準形）
- **CIループ（PR単位）** … 1チケットごとの自動テスト門番
- **回帰評価（リリース単位）** … まとめて品質チェック
- **本番監視（運用単位）** … サンプリング評価1〜5% ＋ ガードレール ＋ コスト計測 の3点セット

### 核心の原則（OpenAI）
- **人間は“別の抽象度”で残る**: 仕事の優先順位づけ／ユーザーの声を受け入れ基準に翻訳／結果の検証
- **エージェントがつまずいたら“何が足りないかの信号”**: ツール・ガードレール・ドキュメントの不足を特定し、**リポジトリに還元**する
- **一度の失敗を二度させない**: ミスのたびにハーネスを改良し、同じ失敗を構造的に潰す

### あなたへの落とし込み（最短の一歩）
- まず**検証ループ層**だけでいい: `gokugen-destroyer` を「合否ゲート」に格上げし、Playwright MCPで実画面テスト
- 次に**コンテキスト層**: 大きな依頼は `/plan` で分割してから回す（コンテキスト不安を防ぐ）
- ガードレール/観測は受注が増えてから。**やりすぎない**（ハーネス弄りは準備＝出荷ファーストに反する）
