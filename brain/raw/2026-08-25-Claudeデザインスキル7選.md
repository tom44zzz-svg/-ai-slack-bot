## 前提

**どのモデルも、設計するとき自分のパターンに従う。そしてそのパターンは見れば分かる。**
だからパターンから引き剥がす仕掛けが要る ← 3本とも同じ診断。

これらのスキルは、**デザインの実務経験がある人が、自分で試して効いたワークフローを
再利用可能な形に固めたもの**。ワークフローが立派に見えても、出てくるサイトが
他と同じなら意味がない、というのが選別の軸。

> 📌 Claude Design 用に別途スキルを足す必要はない。**Claude の設定に入れたものがそのまま使える。**
> Claude Code / Codex など他のエージェントでも同じ結果になる。

## 7セットの比較

### 1. Emil Kowalski — https://github.com/emilkowalski/skills
9個のセット。**動画主が自分たちで実際に使っている**もの。

- **design engineering** … UIコンポーネントの作り方とアニメーションの付け方。**最初に使う**
- **animate** … **すでに出来ているサイト**にアニメーションを足す完全な手順。
  サイトの構造を理解して「どこが動くべきか」を判断する
- apple design … Apple の設計原則を他サイトに持ち込む
- animation vocabulary … **曖昧なアニメーション表現を、モデルが理解できる正確な語に変換する**

効きどころ: LP のような大きな見せ場より、**アプリの機能面の小さな要素**。
フォーム送信時の動き、ホバーで出るグラフィックなど、体験の質が上がる。

### 2. garden-skills（ConardLi） — https://github.com/ConardLi/garden-skills
5個。本命は **web design engineer**。

- 要件を**対話で詰めてから**着手する
- **原則「良いデザインは無から生まれない」** → 実在するデザインを探して土台にする
- 内蔵の参照資料: デザインの評価の仕方 / よくある失敗の型 / Apple・Linear などのスタイルレシピ
- **既存デザインを領域別に採点**できる。満点に近づくまで反復できる

### 3. landing-page-design（elayadesign） — https://github.com/elayadesign/ai-design-skills
単一スキル・1ファイル。アイデアを**ビジュアルシステム**（色・書体・余白のルール一式）に変換。

> **LP はホームページではない。** ホームページは多くの人に同時に応える。
> LP の仕事は1つ、**行動させること**。

モデルは「機能するホームページ」は作れるが、LP に特化してはいない。
このスキルは**取ってほしい行動1つを中心にページを構造化**する。検索での見つかりやすさも扱う。

### 4. Meng To — https://github.com/MengTo/Skills
長年の現役デザイナー。スクロール連動のストーリーテリングで知られる人の型。

- **video to super prompt** … 画面録画やウォークスルーを、ローカルのツールで解析してプロンプト化
- **awwwards quality sites** … 受賞サイトが持つ原則を列挙。
  **原則だけでなく「高そうに見せる」具体的なテクニックと効果まで入っている**のが差。
  モデルが自力では出さない部分

### 5. Jakub Krehel — https://github.com/jakubkrehel/skills
**1スキル1領域に分割**（タイポグラフィ / カラー / アクセシビリティ …）。

- **review** … 全領域を横断レビューして採点。**GitHub に繋ぐと変更前後を比較**でき、
  「前は動いていたのに、この変更で壊れた」と指摘できる。アニメーション・アクセシビリティ・
  各画面幅での崩れを見る
- **better layout** … 余白・配置・整列。**Claude Design が一番弱い領域**。
  「この日付はあと何px必要」まで具体的に言う。見た目が激変はしないが、**原則に対して正しくなる**

### 6. tastemaker（codeswithroh） — https://github.com/codeswithroh/tastemaker
**思想が他と違う。参照画像をテキスト要約にしない。**

通常、参照画像を渡すとモデルはそれをテキストの要約に変換して以後の参照にする。
このスキルは**スクリプトで実際のピクセルから正確なデザイン値を抽出**し、
エージェントが後で使える構造化データとして保存する。
→ **テキスト化の過程で失われる情報を保つ。** 判断はプロジェクト全体に一貫して効く。

### 7. designer-skills（Owl-Listener） — https://github.com/Owl-Listener/designer-skills
**名前のついたデザイン法則**（実際の研究）に根拠を持つ。1法則1スキル。

- **screen critique** … 1画面を多角的にレビューし、どこが間違っているかを列挙
- **perception laws** … **人間の目が実際にどう見て理解するか**。適用すると全体が引き締まる
- 「なぜ人は途中で離脱するのか」なども扱う。**全部入れず、自分の作り方に合うものだけ入れる**

## 使い分けの整理（自分用）

| やりたいこと | 使うもの |
|---|---|
| ゼロから作る | Emil `design engineering` → garden `web design engineer` |
| 出来たものに動きを足す | Emil `animate` |
| LP（行動させるページ） | landing-page-design |
| 「高く見せる」 | Meng To `awwwards quality` |
| **出来たものを採点・修正** | Jakub `review` / `better layout`、designer-skills `screen critique` |
| 参照デザインに忠実に寄せる | tastemaker |

## ②の動画との対立点（面白いので残す）

- **②モチーフ駆動** … 参照画像を **Claude に言語化させて**から作る（テキストを経由する）
- **⑥tastemaker** … **テキスト化で情報が落ちる**として、ピクセルから直接値を抽出する

どちらが正しいというより、**言語化は方向性を決めるのに強く、抽出は再現に強い**、
という役割の違いに見える。両方使うのが筋かもしれない。

## このリポジトリでの当てはまり

- `mock-system/` `/brand-mock` … garden の「評価の仕方・失敗の型」、
  Jakub の `better layout` は**そのまま効きそう**
- 学習図解の HTML … 余白と整列は毎回手で直している。`better layout` 的な採点があれば早くなる
- `business/sales/portfolio.html` … LP に近い性質（1つの行動＝問い合わせに寄せる）

> 📌 未着手: **どれも英語圏のスキル。** ①の動画の結論と同じで、
> 日本語の図解・スライド用には自分で最適化が要る。まず `review` 系を1つ入れて、
> 既存の図解を採点させてみるのが一番安い入口。
